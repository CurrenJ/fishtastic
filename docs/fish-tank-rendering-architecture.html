Fish Tank Rendering Architecture

How Fabric and NeoForge dynamically retexture fish tank blocks at chunk-meshing time

Common (shared)
Fabric
NeoForge

The Core Problem

A normal Minecraft block model is baked once at resource-load time with static textures. The fish tank cannot do this because:

  1. Two tanks in the same chunk may have different frame/sand/glass choices.
  2. Players can change customization at any time — no full resource reload required.
  3. The texture is a property of the block entity, not the block state.

Solution: Both platforms use a dynamic block state model that emits geometry at chunk-meshing time with world context, reads the block entity's current configuration, and retextures on the fly.

Sub-Model System (Shared)

The fish tank is composed of three parts, each with 64 geometric permutations (2&sup6; = 64) for every combination of open/closed faces:

Frame (64 models)
Sand (64 models)
Glass (64 models)

Total: 192 sub-models pre-loaded at resource load time

fishtastic:block/fishtankbase/fish_tank_frame_0 .. fish_tank_frame_63
fishtastic:block/fishtankbase/fish_tank_sand_0 .. fish_tank_sand_63
fishtastic:block/fishtankbase/fish_tank_glass_0 .. fish_tank_glass_63

The permutation index is derived from the openFaces bitmask. At runtime, the correct permutation is selected and retextured from the chosen blocks.

Key Divergence Points

1. World-Context API
Fabric

FabricBlockStateModel.emitQuads(QuadEmitter, BlockAndTintGetter, BlockPos, ...)

QuadEmitter-based — quads are emitted directly into the quad buffer.

NeoForge

DynamicBlockStateModel.collectParts(BlockAndTintGetter, BlockPos, ...)

List-based — returns List<BlockStateModelPart> to be collected.

2. Block Entity Data Access
Fabric

RenderDataBlockEntity.getRenderData()

Interface injected by Fabric API. Snapshot captured on main thread before meshing job dispatch — no explicit synchronization needed.

NeoForge

ModelData property bag

Typed property system. Block entity overrides getModelData() to contribute properties.

3. Blockstate JSON Syntax
Fabric
{ "variants": { "": { "fabric:type": "fishtastic:fish_tank" } } }
NeoForge
{ "variants": { "": { "type": "fishtastic:fish_tank" } } }
4. Item Model Loader
Fabric

UnbakedModelDeserializer.register()

Registered in client init. Uses "fabric:type" in JSON.

NeoForge

UnbakedModelLoader via ModelEvent.RegisterLoaders

Standard Forge event. Uses "loader" in JSON.

5. Blockstate Redirect Resolution Critical
Fabric — Automatic

PreparableModelLoadingPlugin

Runs off-thread during resource reload. Reads all blockstate JSONs, builds a Map<standardPath, actualPath> redirect map. BlockModelPathResolverFabric checks it at texture-lookup time. Missing models are skipped to prevent fallback short-circuit.

NeoForge — Config-driven

FishtasticConfig.STARTUP.blockModelPathOverrides

User-editable config entries with wildcard pattern matching. Standard block/<name> path is always the fallback.

The bakeTopGeometry Cache Bug Fixed

Both platforms had to work around a bug in Minecraft's ModelWrapper.bakeTopGeometry():

// BROKEN: caches by ModelState only, ignoring TextureSlots model.bakeTopGeometry(textureSlots, baker, state) // ┌─ ModelWrapper stores result in fixed slot for IDENTITY // │ forever after first call (wrong texture returned) // └─ Other ModelState values cached by object identity // — reused static states return first result forever

The fix on both platforms: bypass ResolvedModel entirely and call the underlying geometry bake directly:

// WORKAROUND: go straight to UnbakedGeometry implementation model.getTopGeometry().bake(slots, baker, BlockModelRotation.IDENTITY, model, ...)

The particle material has the same issue — both platforms call the static resolveParticleMaterial(slots, baker, model) overload to bypass the cached KERNEL_PARTICLE_SPRITE slot.
