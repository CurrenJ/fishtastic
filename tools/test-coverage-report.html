What's solid strengths

Worm Bin economy is the best-tested feature in the mod12 shared test methods cover phase transitions (EMPTY → CONVERTING → READY), the 5-fish deposit cap, the 5-turn aeration cap, base vs. aeration-reduced conversion timing (6000 → 4800 ticks), per-quality worm yield math, mixed-quality batches, and harvest/reset. This is the template the rest of the mod should follow.
Fish-catch leaderboards have real edge-case coverageGuard clauses (non-fish items, zero-size fish), personal-vs-global isolation by UUID, sort-order correctness (asc/desc), and unknown-player handling are all explicitly asserted — exactly the kind of off-by-one / data-isolation bug that's painful to catch by hand.
Core data components are verified end-to-endItemSize and FishQuality round-trip through get/set/remove/copy and the empty-stack no-op guard; all 5 quality tiers and their render-effect thresholds and intensity values are checked; BaitEffect presets (WORMS, BLAZED_GRUB, GUMMY_WORMS, NO_BAIT) are pinned to documented numeric values.
Genuine cross-platform parity, not just "compiles on both"All 35 test methods live once in common/src/testmod and run unmodified on both Fabric (@GameTest + fabric-gametest-api-v1) and NeoForge (programmatic RegisterGameTestsEvent) — a Fabric-only regression in shared logic would still be caught on NeoForge's run and vice versa.

Where to focus manual QA gaps, prioritized

Critical

Fishing minigame core (session generation & trust validation)

FishingMinigameManager (458 lines) implements a trust-based model: the server generates and caches loot for a session, the client plays the minigame locally, and the server validates the client's reported results before awarding anything. That validation boundary is exactly the kind of logic an automated test should pin down — right now nothing does. FishingTarget (907 lines, the largest util class in the mod), FishingMinigameAnimation (506 lines), and FishingMinigameState (268 lines) are all likewise untested.

Manual QA focus: try to win the minigame with implausible inputs (replayed/edited client reports if you can simulate them), check reward correctness across temperaments/biomes, and watch for any path where a session can be double-claimed or left dangling across a disconnect.
Critical

Fish Tank system

FishTankBlockEntity (848 lines) is the largest block entity in the mod and has zero automated coverage, alongside customization-mode management, edit-mode state, and the composite-model/cosmetic-grid placement logic (31 files total in this domain). This is exactly the size/complexity profile where regressions hide.

Manual QA focus: customization mode entry/exit, cosmetic placement at grid edges, save/reload of tank contents, and behavior when the tank block is broken/moved mid-edit.
High

Quests & Tutorial (newest feature, no tests yet)

The most recent commit on this branch ("Implement fishing and quests flow tutorial") shipped QuestTracker, PlayerQuestState, TutorialManager, and their packet/UI plumbing — 21 files — with no automated coverage at all. New code is statistically where the next bug lives.

Manual QA focus: daily quest reset boundary (midnight rollover, server restart mid-day), quest progress sync after reconnect, and tutorial step skipping/replay.
High

Item Effects engine

ItemEffect (323 lines) plus a small condition-combinator system (AndCondition, ComponentCondition, ComponentValueCondition, ItemTagCondition) forms a little rule engine. This is the kind of branchy, deterministic logic that's cheapest to unit-test and most expensive to verify by hand — the gap here is more about effort than risk.

Manual QA focus: stack conditions that should AND together but might short-circuit wrong; verify effects keyed on item tags still apply after a tag-data change.
Medium

Networking — no packet round-trip tests

10 custom payload classes (leaderboard request/response, quest sync, tutorial sync, minigame start/finish, shop purchase, customization mode) all use hand-written StreamCodecs with no encode→decode round-trip assertions. Bugs here are silent on a single-player test and only surface as multiplayer desync.

Manual QA focus: test specifically in a real client/server split (not single-player integrated server) — desync bugs don't reproduce there.
Medium

Shop / Economy & Datagen validation

ShopEntry + PurchaseShopEntryPacket (the fishing token shop from a recent commit) have no tests around price/affordability/double-spend edge cases. Separately, the 8 datagen providers (recipes, loot tables, tags, models) have no "did this generate something sane" check.

Manual QA focus: rapid double-click purchase attempts; spend-to-exactly-zero balance; regenerate datagen output after any item/recipe change and diff it.
Low

Pure utility math — untested but trivial to fix

MathUtil (110 lines) and Utility have no world-state dependency at all — they're the cheapest possible GameTest (or even plain static-method) candidates and currently sit at zero coverage for no good reason.

Manual QA focus: low priority — this is better spent as a quick automated-test addition than manual checking.
Low

Client rendering, GUI & Mixins — out of scope by design

46 files (25 client rendering/GUI, 21 mixins) cannot be reached by the GameTest framework at all — it runs headless against a server, never a render thread. This isn't a hole in effort, it's a hole in what this tool can ever cover.

Manual QA focus: this is genuinely the right tool for the job. Visual checks on fish tank rendering, item glint/outline effects, GUI screens (quest log, leaderboard), and HUD notifications belong here permanently.
Low

Housekeeping: one dead file

common/src/main/java/grill24/fishtastic/server/FishingLootHelper.java is a 0-byte file with no references anywhere in the codebase — not a coverage gap, just leftover scaffolding worth deleting.

Manual QA focus: none — delete it.
Methodology. This project has no instrumented line-coverage tool (no JaCoCo/JUnit task in any build.gradle); its only automated tests are Minecraft's GameTest framework, run server-side via ./gradlew :fabric:runGametest / :neoforge:runGametest against the shared common/src/testmod source set. "Coverage" above means structural domain coverage — whether at least one test exercises a class — derived by reading all 196 main-source files across common/, fabric/, and neoforge/ and cross-referencing them against every class referenced from FishCatchDataGameTests.java, ItemComponentGameTests.java, and WormBinGameTests.java (the three shared test files, currently staged/uncommitted on branch 26.1.2). Two stale agent worktrees contain an abandoned MultiItemPhysicsTest.java for PhysicsSimulation that never landed on this branch — physics testing was attempted but isn't part of the current suite. Domain buckets are mutually exclusive by file path/name pattern and sum exactly to 196.
