# Plan two ports around rendering risk

**Minecraft 26.2 and 26.3 are credible future targets, but neither is a dependency-only update.** The strongest recommendation is to preserve the current multiloader design, port Gelatin UI alongside Fishtastic, stabilize 26.2 first, and derive 26.3 from that reviewed baseline. Both versions change rendering contracts used by this mod; 26.3 additionally breaks the current outline atlas technique and native mouse polling. Upstream loader and build-tool families exist, which makes investigation worthwhile, but their availability does not establish a working Fishtastic/Gelatin combination. Start any future implementation with bounded toolchain, Gelatin, and outline-rendering proofs before committing to a release date. Treat Fabric and NeoForge as the default four new release cells; Forge is an independent, conditional addition. **CoolCam is development support only: do not port it, require it for target compilation, bundle it, or make it a release dependency.** This report is an audit and future plan; it includes no implemented port and no executed target compatibility tests.

Audit date: **19 October 2026**. Source snapshot supplied by the repository audit: branch `26.1.2`, HEAD `0b84e7e327e9317ebd77c6fb61d418bb33329cdf`, plus a dirty working tree. File links describe that inspected tree and can move as development continues. This is not a frozen release baseline.

## Feasibility depends on library and rendering proofs

### The verdict is conditional for each target

| Target | Engineering assessment | Primary condition before a delivery commitment | Proposed first release scope |
|---|---|---|---|
| 26.2 | Feasible in principle; substantial rendering and GUI port, medium-to-high implementation uncertainty | Gelatin screens and Fishtastic item/tank rendering work with staged submission; exact loader/toolchain tuple resolves and transforms common code | Fabric and NeoForge, each independently accepted |
| 26.3 | Feasible in principle; higher risk and wider API change than 26.2 | Explicit outline-atlas render passes, migrated shaders/GPU resources, SDL input and Gelatin text focus all work on actual target builds | Fabric and NeoForge, after or independently gated from 26.2 |
| Optional Forge on either target | Plausible additional lane, not part of the default commitment | Reviewed current Forge baseline, target transforms/networking/library artifacts, installed client/server and release metadata gates | Only the exact target cells that pass their own gates |

The code offers useful advantages: loader-specific adapters are already separate, the tank renderer already distinguishes state extraction from submission, and the Minecraft-independent simulation engine has substantial tests. These reduce the amount of conceptual redesign. They do not remove the need to adapt rendering hooks, mixins, datagen and dependency distribution. The largest uncertainty is the integration of custom GPU effects with the new submission model, including the required Gelatin UI library. The absence of direct `org.lwjgl.opengl` imports in the four audited main source roots is encouraging for backend portability, but does not prove Vulkan support or correct custom passes. ([Local source audit](../research_notes/Minecraft%20forward%20port%20feasibility/source-audit.md), [tank renderer](../common/src/main/java/grill24/fishtastic/client/renderer/FishTankBlockEntityRenderer.java))

### Preserve the existing product boundaries

The assumed target is feature parity with a deliberately selected current baseline: catching and quality, quests/tutorials, shops, encyclopedia, tanks and cosmetics, companions, ambient fish, networking, save data, UI effects and optional JEI integration. A future kickoff must record exactly which uncommitted features belong in that baseline. This audit does not quietly treat the current dirty checkout as a tested release or propose dropping complex visuals to meet a date.

Released artifacts should continue to contain the required transformed common code and shaded fishsim engine while requiring separately distributed Gelatin UI. The standalone tank generator, development selftests and cinematic support are development tools. CoolCam currently appears as Fabric `compileOnly`/`localRuntime`, and its optional bridge directly references its API from main sources. Future target builds should exclude or isolate that bridge so that **zero CoolCam artifact is needed for a target release build**. Existing optional capture checks can use vanilla camera/screenshot paths or be excluded from cinematic evidence; required static visual acceptance must remain. This is Fishtastic build isolation, not a CoolCam port. ([Fabric build](../fabric/build.gradle), [optional bridge](../fabric/src/main/java/grill24/fishtastic/fabric/compat/coolcam/CoolCamFollowBridgeImpl.java), [selftest harness](../common/src/main/java/grill24/fishtastic/client/selftest/RenderSelfTest.java))

No Architectury runtime API dependency was found in the inspected build or metadata. The project uses Architectury build plugins and `ExpectPlatform` annotations from injectables. Consequently, Architectury API migration documents do not create a runtime-library port requirement here. Preserve the existing service/transform boundaries unless an actual target incompatibility justifies changing them. ## The current code exposes two distinct migration steps

### 26.2 already requires rendering migration

Upstream 26.2 introduces Vulkan alongside OpenGL and reverse depth, removes `MultiBufferSource`/`OutlineBufferSource`, and stages rendering through prepared render types. Font batching and picture-in-picture contracts also change. These last two require a Gelatin audit; no direct Fishtastic `drawInBatch` or `PictureInPictureRenderer` match was found. Screen access moves under the GUI object, and datagen moves toward block/item keys. These are target deltas, not a complete account of local edits. ([NeoForge 26.2 primer](https://docs.neoforged.net/primer/docs/26.2/), [Fabric 26.2 migration](https://fabricmc.net/2026/06/15/262.html)) Pack targets are data **107.1** and resources **88.0**. ([Official 26.2 technical notes](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-2))

The renderer package should define invariants before changing hooks: simulation/state extraction must not consume rendering state, draw submission must not mutate gameplay, GUI atlas production must complete before consumers read it, and temporary buffers/textures must have a documented owner and lifetime. Reverse depth makes inherited depth-test assumptions suspect; compare against target vanilla pipelines rather than changing depth constants by trial and error. Preserve every supported item presentation so a working tank scene cannot conceal a broken inventory effect.

### 26.3 adds an explicit atlas and input redesign

Upstream 26.3 replaces GLFW with SDL3, changes native key/mouse codes, and requires text focus to reach `TextInputManager`. GPU APIs move into Renderpearl. Global output texture overrides are removed in favor of explicit render-pass attachment control; shader layouts also change. Recipes/advancements join reloadable registry infrastructure. This combination crosses rendering, UI, resources and server data lifecycles. ([NeoForge 26.3 primer](https://docs.neoforged.net/primer/docs/26.3/), [Fabric 26.3 migration](https://www.fabricmc.net/2026/09/15/263.html)) Pack targets are data **121.0** and resources **97.1**. ([Official 26.3 technical notes](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-3)) Text-input examples differ across historical documentation; use exact pinned target sources for method owners and signatures. ([Fabric documentation issue](https://github.com/FabricMC/fabric-docs/issues/730))

## Future work should pass small independent gates

### Keep one Minecraft line per branch and prove 26.3 risk early

The recommended future structure is a dedicated 26.2 branch/worktree and a dedicated 26.3 branch/worktree in **both** Fishtastic and Gelatin, starting from reviewed commits. Keep common/platform separation inside each line and preserve the shared fishsim boundary. Deliver 26.2 first, then carry its reviewed fixes into 26.3; run an early, disposable 26.3 dependency/atlas prototype so a late fundamental blocker cannot surprise the project. This report does not create those branches or prescribe exact branch names without future implementation authorization.

Changing only the root version property is inadequate. JEI artifact names and metadata are hardcoded; all loader modules are included unconditionally even when `enabled_platforms` excludes one; launcher scripts bake current-version details; datagen and packaging have target-sensitive behavior. Future configuration must make the supported module set explicit so deferring Forge actually prevents its configuration/dependency resolution. Avoid introducing a new preprocessing/multiversion framework during these ports unless measured source divergence justifies its separate cost. ([Settings](../settings.gradle), [root build](../build.gradle), [common build](../common/build.gradle), [installed Forge launcher](../scripts/run-installed-forge-client.ps1))

If the current build technology cannot support a target, native Fabric Loom, NeoForge ModDevGradle or ForgeGradle are possible fallback investigations. They must reproduce common transformation, injectables, access configuration, fishsim shading, development runs, tests and publication wiring. That is a separate architecture package and estimate, not a routine plugin bump.

## Release evidence must cover every advertised cell

### Existing tests provide breadth, not current target proof

The audit found **48 common JUnit files, 107 fishsim JUnit files, one tank geometry test file and 37 shared testmod files**. Raw source searches counted 666 `@Test` annotation lines and 387 GameTest-shaped method lines. Those are inventory signals, not executed or even discovered test totals. Fabric and NeoForge already configure GameTest runs, with NeoForge source-set/datagen wiring that needs careful preservation. Future acceptance must compare discovered Fishtastic test IDs with a baseline manifest and reject a green task that silently discovers nothing. ### Distribution and rollback are part of feasibility

The current root release task targets Fabric and NeoForge and relies on required Gelatin relationships. A future release path should accept an explicit list of validated cells instead of uploading every configured module. Refresh exact game-version tags, Java tags, dependency bounds, JEI optional metadata and unique beta version strings. Rehearse on a clean checkout/cache without `mavenLocal` and inspect packaged resources so ignored generated output cannot mask a missing datagen step. Resolve and publish the library before releasing a consumer that requires it. ([Root publication wiring](../build.gradle), [datagen helper](../scripts/run_datagen.bat), [ignore rules](../.gitignore), [dependency research](../research_notes/Minecraft%20forward%20port%20feasibility/dependencies-strategy.md))

World-upgrade fixtures must be disposable copies. Preserve original worlds and matching baseline mod/library artifacts before any new-version launch. **Rollback means restoring the original game/mod tuple and original world backup**; opening an upgraded save in an older Minecraft version is not an accepted rollback procedure. Keep hashes and release notes for every candidate, including failed candidates, so support can identify exactly what a user ran. A failing cell should be deferred or superseded without forcing rollback of independently accepted cells.

## Budget for the whole product and ongoing support

### Estimates are planning ranges with explicit assumptions

The following estimates are engineering judgment, not measured implementation throughput. They assume one experienced maintainer familiar with the repository, Java 25 remains viable, upstream artifacts are available, Gelatin is under project control, existing tests are reusable, no new gameplay scope is added, and the current build technology works after bounded probes. A day means focused engineering time; external repository indexing, maintainer response and hardware scheduling add elapsed time. Each row includes implementation and local defect fixing for that scope; dedicated acceptance is separate. The rows deliberately avoid counting an additional build-only estimate on top of the same work.

| Work package group | Engineer-days | Included work and uncertainty |
|---|---:|---|

| P08: 26.2 acceptance | 2–4 | Discovered tests, installed cells, multiplayer, upgrades, graphics/performance review; major redesign excluded |

| Explicit uncertainty reserve | **25–35%** | Unmeasured rendering/backend defects, library redesign and source/API surprises |

| Optional Forge across both versions | **Add 3–8, then revise after its probe** | Adapter/tooling/distribution acceptance only; unfinished current-line work or major shared rendering defects add separate cost |

These numbers are intentionally broader than a build/dependency-only allowance. The source audit establishes several guaranteed API conflicts but cannot estimate the number or severity of runtime regressions without compiling and rendering. Treat the range as a budgeting envelope and re-estimate immediately after P03/P07. A toolchain replacement, major Gelatin rewrite or unsupported render behavior requires a new estimate rather than consuming reserve silently.

The critical path is **baseline → target toolchain → Gelatin render/menu proof → invasive Fishtastic rendering proof → subsystem completion → installed acceptance → remotely available library → consumer release**. P07 can expose 26.3 problems early while 26.2 core work continues. Optional Forge should not extend the default critical path unless simultaneous three-loader delivery becomes an explicit requirement. Testing hardware or dependency publication can dominate elapsed time even when source work is finished.

### Maintenance is four new cells plus the library

Keeping both lines means four additional Fabric/NeoForge game-version/loader artifacts, matching library artifacts and independent installed client/server acceptance on every coordinated release. Optional Forge adds two more cells. Record where each fix originates, which lines require it, the cherry-pick or adapted commit, and the tests proving equivalence. Preserve fishsim source behavior across lines and avoid engine forks driven by rendering adapters.

As an initial maintenance allowance, reserve **0.5–1.5 engineer-days per routine synchronized release** for additional build/test/packaging triage across the four cells, or **1–3 days for a release involving loader/API breakage**; optional Forge and major regressions are additional. Replace these planning assumptions with measurements from the first two release cycles. If the project cannot sustain that matrix, reduce promised release cadence or target-cell scope before adopting a new multiversion build framework merely to hide divergence. ([Maintenance/build analysis](../research_notes/Minecraft%20forward%20port%20feasibility/dependencies-strategy.md))

### What this audit established and what it did not execute

The research performed read-only repository inspection, source searches/counts, build/metadata/script review, current Forge-progress review, and upstream documentation/artifact-index research. It identified direct code exposure and candidate upstream families. It did **not** compile either target, resolve a complete target dependency graph, inspect every exact target method signature, run JUnit/GameTests, generate target data, launch clients/servers, validate final JAR contents, capture target rendering, benchmark a port, migrate a world, create target branches or publish anything. Existing Forge checkpoint results are historical evidence about the current line, not newly executed results or target certification.
