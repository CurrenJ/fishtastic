# Forge build and toolchain review

## Which build approach is justified by current evidence?

### Takeaway
Use Architectury Loom 1.17 as the first implementation route for both versions. The earlier broad outline understated upstream support: 1.17 explicitly repaired Forge 1.21.x and 26.x, including real unobfuscated Forge patching code. Local success remains unverified; no builds or clients were launched in this investigation.

### Cited Findings
- Forge download pages checked 2026-10-18 report 1.21.1 latest 52.1.20/recommended 52.1.0 and 26.1.2 latest 64.1.5/recommended 64.1.0. Pin selected coordinates rather than dynamic latest. — [Forge 1.21.1](https://files.minecraftforge.net/net/minecraftforge/forge/index_1.21.1.html), [Forge 26.1.2](https://files.minecraftforge.net/net/minecraftforge/forge/index_26.1.2.html).
- Architectury Loom 1.17 release lists Forge 1.21.x/26.x fixes and new AW conversion on final jar tasks. — [Release](https://github.com/architectury/architectury-loom/releases/tag/1.17).
- PR 343 merged 2026-06-17 addresses newer Forge development launch, classpath and bootstrap problems; PR 349 merged 2026-06-22 completes unobfuscated Forge merge/manifest handling and adds Forge261/262 integration tests. These are upstream evidence, not this mod's test results. — [PR 343](https://github.com/architectury/architectury-loom/pull/343), [PR 349](https://github.com/architectury/architectury-loom/pull/349).
- Actual implementation is present: MinecraftPatchedProvider lines 234–247 creates a manifest and merges userdev; lines 268–274 select MCP `merge` for Forge versus `preProcessJar` for NeoForge. — [Source](https://github.com/architectury/architectury-loom/blob/dev/1.17/src/main/java/dev/architectury/loom/forge/minecraft/MinecraftPatchedProvider.java#L234).
- CompileConfiguration lines 209–248 checks the remap/no-remap choice and runs the unobfuscated Forge patch/dependency pipeline without mappings. Therefore support is materially stronger evidence than the FORGE enum or a generic README claim. — [Source](https://github.com/architectury/architectury-loom/blob/dev/1.17/src/main/java/net/fabricmc/loom/configuration/CompileConfiguration.java#L209).
- ForgeProvider `usesMojangAtRuntime()` selects Mojang production namespace for Forge majors >=50. Constants explicitly fixes the boundary at 50 (Minecraft 1.20.6). Forge 52 for 1.21.1 consequently does not share Forge 47's SRG production namespace. — [Provider](https://github.com/architectury/architectury-loom/blob/dev/1.17/src/main/java/dev/architectury/loom/forge/dependency/ForgeProvider.java#L54), [Constants](https://github.com/architectury/architectury-loom/blob/dev/1.17/src/main/java/net/fabricmc/loom/util/Constants.java#L219).
- Forge's current 26.1.2 MDK uses ForgeGradle `[7.0.17,8)`, Java 25, `minecraft.dependency(...)`, eventbus-validator annotation processing and client/server/gameTestServer/data runs. This is a credible fallback baseline rather than an unproven old ForgeGradle 6 template. — [MDK](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/mdk/build.gradle).
- Upstream source URLs above use a moving branch. At implementation kickoff pin a concrete Loom artifact and record its resolved version/hash and source commit containing both merged fixes. A cached jar's presence alone is no proof of compatibility. — [Release](https://github.com/architectury/architectury-loom/releases/tag/1.17).

### Inferences
- Preferred 26.1.2 route: upgrade `dev.architectury.loom-no-remap` from 1.14-SNAPSHOT to a pinned 1.17 build, prove existing Fabric/NeoForge tasks still configure/build, then add Forge using the same plugin family. This avoids maintaining two competing Minecraft toolchains.
- Preferred 1.21.1 route: keep regular remapping Loom 1.17 and official Mojang mappings; add Forge platform transformation alongside existing Fabric/NeoForge. A Mojang-named common class artifact is a plausible compatible input, but classpath attributes and production Mixin behavior still require a packaged-jar probe.
- Do not copy 1.20.1's SRG refmap injection, manual MixinExtras bootstrap/shading, or JEI classpath filtering blindly. Those comments document failures for Forge 47 and are useful regression cases, not established requirements for Forge 52/64.
- Start with latest pinned Forge builds for development, then test the advertised minimum before declaring a lower metadata floor. Using recommended versions as an automatic minimum has no code-level justification yet.

### Gaps
- No local proof that Loom 1.17 plus this project's Shadow plugin, Gradle wrapper and Architectury transformation combination works on either new Forge target.
- The exact preferred immutable Loom 1.17 artifact should be resolved and recorded during implementation. Local Gradle caches contain 1.17.491 and 1.17.493, but their presence does not establish which fixes they include.
- No exact supported ForgeGradle 7/Gradle-wrapper coexistence was exercised. Validate the chosen MDK wrapper if fallback is needed, rather than imposing this repo's wrapper without checking.

## What exactly must change in the repository and artifacts?

### Takeaway
Add a third loader module per target branch and preserve their distinct artifact pipelines. The 26.1.2 shipped artifact is the processed shadow jar; the 1.21.1 artifact comes through remapJar. Keep common gameplay shared, with Forge-specific platform transformations and access conversion.

### Inferences
- Modify per branch: `settings.gradle`, `gradle.properties` (Forge version/ranges/platform list), root `build.gradle` (plugin pin and publish artifact), new `forge/build.gradle`, new loader-specific `forge/gradle.properties` if needed, `forge/src/main/resources/META-INF/mods.toml`, Forge mixin JSON, Forge platform source and implementations, plus GameTest source/resources. Make equivalent Gelatin changes before Fishtastic requires its new Forge artifact.
- 26.1.2 module outline: architectury platform setup + forge(); Forge dependency; common direct project input with transformProductionForge; fishsim dev and bundle inputs; current processed-jar-base shadow pattern; explicit AW conversion on final `shadowJar` after transformed common has been bundled. Register common + Forge Mixin configs in dev and ensure production manifest contains them. Verify Gradle task execution order rather than assume Shadow doLast hooks compose with AW conversion.
- 1.21.1 module outline: namedElements for development common, transformProductionForge for bundled common, dev-shadow intermediate, remapJar final input, unique refmap names retained. Inspect final namespace and mixin metadata; keep common remapJar disabled unless evidence justifies changing that existing guard.
- The Forge ExpectPlatform classes must use exact package/name convention expected by Architectury. Verify bytecode has calls to Forge implementations and no untransformed AssertionError/RuntimeException placeholders on a representative registration/config/storage call.
- Publishing must add Forge upload with Gelatin dependency, Forge loader tag, Minecraft and Java tags and correct final archive. Include Forge build in dependsOn; Maven outgoing variants/publications must also point at the final distributable. Do not upload dev-shadow/raw jars.
- Reuse generated common resources as far as possible, retain Forge-specific model JSON where loaders differ. Audit final assets/data entries rather than indiscriminately copying Fabric-generated files. Extend explicit copy scripts only if Forge actually needs platform copies.
- Keep testmod, MCP bridge, self-test and fishsim rendering/harness/viewer exclusions synchronized with current packaging policy. Prove shipped fishsim runtime classes exist and dev-only classes do not; do not omit runtime simulation packages on the assumption they are test tooling.

## What are the ordered implementation gates and fallbacks?

### Takeaway
Resolve toolchain and final-jar correctness before large adapter implementation. Each gate needs exact coordinates, commands, expected artifact/result, logs and the next pending action; a successful Gradle exit without discovered tests or a packaged-jar launch is insufficient.

### Cited Findings
- Current root baseline at inspection: branch `26.1.2`, HEAD `0b84e7e3`; tracked edits in CHANGELOG.md, build.gradle, ambient command/runtime Java, docs/README.md, docs/fish-in-world.md, fabric/build.gradle, fabric.mod.json, gradle.properties, ideas.txt, NeoForge metadata; untracked catch-up plan/progress/ledger directory. Preserve these unrelated changes. Worktree inventory reports `port/1.21.1` at `e06344aa`, `port/1.20.1` at `e7ff95df`; content is moving while other work proceeds. — Local `git status --short`, `git branch --show-current`, `git worktree list` observed 2026-10-18; source file baselines linked above.
- Wrappers differ: current 26.1.2 is Gradle 9.2.1; inspected 1.21.1 is Gradle 9.5.0. Do not assume one shared wrapper/toolchain. — [26 wrapper](D:/GitHub/fishtastic/gradle/wrapper/gradle-wrapper.properties:3), [1.21 wrapper](D:/GitHub/fishtastic-worktrees/mc-1.21.1/gradle/wrapper/gradle-wrapper.properties:3).
- Current GameTest helper creates unique worlds, keeps failed worlds, removes only verified in-root successful worlds. NeoForge explicitly combines main and testmod into the default main mod group to avoid silent discovery loss. 1.21.1 also adds fishsim to that group for module visibility. — [world helper](D:/GitHub/fishtastic/gradle/gametest-world.gradle:1), [26 discovery](D:/GitHub/fishtastic/neoforge/build.gradle:145), [1.21 grouping](D:/GitHub/fishtastic-worktrees/mc-1.21.1/neoforge/build.gradle:174).
- 1.21.1 common test harness contains a separate compile-only NeoForge annotation stub artifact. Forge cannot rely on NeoForge's annotation identity to discover its tests. — [common test wiring](D:/GitHub/fishtastic-worktrees/mc-1.21.1/common/build.gradle:12).

### Inferences
1. **Baseline gate:** implementation starts by recording clean/dirty state and exact HEAD for both mods and version worktrees. Keep loader work isolated and do not reset ongoing changes. Record complete version/build tool matrix, dependency coordinates and port-parity baseline before touching code. This investigation did not continue the backport catch-up operation or advance its markers.
2. **Upstream toolchain gate:** make a minimal disposable Forge module on pinned Loom 1.17 for each version. First prove dependency resolution, compile, jar, launch configuration, dedicated server and client boot. Add one common ExpectPlatform call and one widened Minecraft access so the probe exercises transformations instead of merely loading an empty mod. Initially omit optional JEI/CoolCam.
3. **Regression gate for 26.1.2 upgrade:** build current Fabric/NeoForge with the new Loom and run their established smoke/tests before attributing later failures to Forge adapter code. Keep no-remap/Java 25; keep regular Loom/mappings/Java 21 on 1.21.1.
4. **Artifact gate:** inspect and launch the actual final jar outside the Gradle dev runtime. Assert common transformed classes, fishsim runtime classes, Forge metadata, correct MixinConfigs, AT contents, dependency floor and namespace. Run one common Mixin behavior and widened menu/render access on client plus dedicated server boot. Dev boot alone does not pass.
5. **Gelatin dependency gate:** same toolchain + final artifact checks in Gelatin, menu registration and screen opening. Publish only local test artifacts until both dependency and consumer validate.
6. **Adapter and tests gate:** implement platform features with smoke checks incrementally. Explicit Forge GameTest wrapper/registration must delegate to loader-neutral logic; split the existing 1.21.1 harness if necessary to avoid importing NeoForge annotations into Forge. Log expected named test inventory/count and compare discovery with execution. Reuse unique-world helper and include main/testmod/fishsim in recognized mod class roots as needed. A vanilla/default-only test run fails the gate.
7. **Release gate:** common/fishsim tests, Forge GameTests, Forge render/self-test scenarios, clean packaged client/server, two-client networking/persistence/reload, dependency-negative checks and both existing-loader regressions after shared changes. Capture exact jar hashes and metadata. Exercise selected minimum plus latest versions if metadata advertises a range. Add CI only after reproducible local commands and reports are established; no current checked-in CI can simply be expanded.

Decision tree / stop conditions:
- **Loom 1.17 probe succeeds:** proceed with one Architectury build family, no new ForgeGradle toolchain.
- **Probe fails in own metadata/package/adapter code:** fix the concrete fault; do not classify it as upstream toolchain incompatibility.
- **Probe reproduces a Loom defect with minimal mod:** retain minimal repro/log/resolved versions. Check whether the chosen resolved artifact includes PR343/349. Permit one bounded correction/pin to a verified newer build; stop broad loader implementation until development and final-artifact probes pass.
- **Toolchain still fails:** use ForgeGradle 7 standalone minimal MDK as discriminator. If MDK also fails, diagnose JDK/environment/upstream version rather than rebuilding project architecture. If MDK succeeds and Loom fails, document the reproducible Loom blocker and choose contained fallback explicitly.
- **Fallback preferred form:** separate ForgeGradle included/standalone build with an explicit exported common artifact (or controlled common sources) and stable shared resources; avoid applying ForgeGradle and Loom to the same project. Root applies Loom unconditionally today, so an ordinary added subproject would need exemption and careful plugin classpath isolation; an included build with its own wrapper/runtime boundary is the safer initial experiment.
- **Fallback costs:** supply ExpectPlatform production transformation and Environment stripping/rewriting that Loom+Architectury previously performed; bridge common classpath without polluting it with platform-only types; convert/package ATs; configure Mixin dev/prod metadata; bundle fishsim and enforce exclusions; publish outgoing artifact; reproduce testmod class roots and runs. On 1.21.1 additionally align mapped dependency inputs and production namespace; never consume the disabled common remapJar or assume a Fabric intermediary artifact loads on Forge. Source-sharing with a Forge compile is an alternative with its own duplicate compilation/API-leak risk, not a free configuration switch.
- **No route produces client, server and packaged-artifact success:** stop and report the exact unmet gate. Do not mark Forge supported or begin publishing on the basis of source compilation alone.

### Gaps
- All proposed commands/gates are future work. No fresh compilation, GameTest, profile, client, server or production-jar evidence was produced here.
- Historical successful 1.20.1 comments and backport logs are implementation references; their applicability to these new loader/version pairs has not been demonstrated.
