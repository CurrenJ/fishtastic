# Fishtastic Forge runtime adapters: 26.1.2 and 1.21.1

## Which runtime architecture should the implementation retain?

### Takeaway

Implement a third loader module on each existing Minecraft branch. Retain that branch's common gameplay and rendering abstractions. The 1.20.1 Forge module is a reference for behavior and registration timing, not a source tree to copy wholesale. The strongest newly verified network candidate is Forge's **PayloadChannel**, which already accepts CustomPacketPayload types and StreamCodec on both requested branches.

### Inferences

- Gate every @ExpectPlatform target and environment annotation in both development and the final jar. A successful common compile does not prove Forge runtime compatibility.

- Local searches did not find an active tracked newer-version `NetworkApiSided` generator/Groovy script. ## How should registration, networking, lifecycle, configuration and persistence be implemented?

### Takeaway

Registration must preserve real Holder semantics, and networking needs a send abstraction as well as a receive registrar. Forge supplies a payload-oriented channel that may avoid changing the common registrar interface; validate this first with registry-bearing ItemStacks on a dedicated server. Companion storage requires explicit Forge persistence and synchronization rather than translating NeoForge AttachmentType imports.

### Cited Findings

#### Registration and initialization

- New loader entrypoint must cover nine static vanilla registries: item, block, block entity type, data component type, creative tab, sound event, particle type, menu, recipe serializer. Current NeoForge central register declarations list them. Data components are queued before items; block-item creation and valid-block arrays must remain lazy where registration is delayed. Dispenser behaviors run in enqueued common setup because they dereference registered holders and mutate vanilla global state. [register declarations](../../neoforge/src/main/java/grill24/fishtastic/neoforge/FishtasticRegistriesNeoForge.java:16), [NeoForge entry](../../neoforge/src/main/java/grill24/fishtastic/neoforge/FishtasticNeoForge.java:50), [adapter](../../neoforge/src/main/java/grill24/fishtastic/architectury/neoforge/NeoForgeRegistrationApi.java:46).
- Forge RegistryObject is a Supplier, not a vanilla Holder. Calling get before registration throws. getHolder is optional and is not promised available during construction. Returning a cast RegistryObject as Holder or calling getHolder().orElseThrow in mod construction is invalid. [Forge 1.21.1 RegistryObject](https://github.com/MinecraftForge/MinecraftForge/blob/1.21.1/src/main/java/net/minecraftforge/registries/RegistryObject.java#L23).
- Existing 1.20.1 Forge registration deliberately invokes common registration functions within the matching RegisterEvent and returns the registry's real Holder.Reference. It queues block items until ITEM registration and throws on a mismatched event. This was necessary for holder identity comparisons. It also registers loader-specific tank block entities and exposes built-in registry accessors. [1.20.1 adapter](D:/GitHub/fishtastic-worktrees/mc-1.20.1/forge/src/main/java/grill24/fishtastic/architectury/forge/ForgeRegistrationApi.java:41), [entrypoint](D:/GitHub/fishtastic-worktrees/mc-1.20.1/forge/src/main/java/grill24/fishtastic/forge/FishtasticForge.java).
- Seven datapack registries require both disk and network codecs: ITEM_EFFECT, FISH_PROFILE, TEMPERAMENT, QUEST, SHOP_ENTRY, FISH_ENCYCLOPEDIA_ENTRY, COSMETIC_STRUCTURE. Omitting the network codec silently breaks client consumers. Their current NeoForge registrations pass the same CODEC twice; codec initialization and cross-registry references must retain startup ordering. [all seven registrations](../../neoforge/src/main/java/grill24/fishtastic/neoforge/FishtasticNeoForge.java:97), [keys](../../common/src/main/java/grill24/FishtasticRegistries.java), [quest cross-registry field](../../common/src/main/java/grill24/fishtastic/data/Quest.java:27).
- Forge 26.1.2's MinecraftForge.EVENT_BUS is a migration helper around the new BusGroup.DEFAULT. IModBusEvent events belong to the mod BusGroup. A mechanical NeoForge IEventBus import substitution will not establish correct event wiring. Model events expose their own static BUS instances in the reviewed source. [MinecraftForge](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/src/main/java/net/minecraftforge/common/MinecraftForge.java#L27), [ModelEvent](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/src/main/java/net/minecraftforge/client/event/ModelEvent.java#L30).

#### Networking: preferred prototype and fallbacks

- Existing FishtasticPackets.IPacketRegistrar takes a `CustomPacketPayload.Type<T>`, `StreamCodec<? super RegistryFriendlyByteBuf,T>`, handler, and direction. There are 20 C2S and 16 S2C registration calls in the reviewed source. The codec-only S2C list is separately maintained for Fabric servers; new packet additions must cover both lists. [registry](../../common/src/main/java/grill24/fishtastic/network/FishtasticPackets.java).
- NeoForge registration uses version 1.0.0 and optional() and delegates IPacketContext enqueueWork/player to IPayloadContext. Current handlers generally enqueue work themselves. Registering a channel alone does not establish a matching send path. [NeoForge registrar](../../neoforge/src/main/java/grill24/fishtastic/architectury/neoforge/NeoForgePacketRegistrar.java:26), [server handler example](../../common/src/main/java/grill24/fishtastic/network/FinishFishingMinigamePacket.java:46).
- Both requested Forge branches have PayloadChannel, an identifier-keyed channel whose flow.add takes vanilla payload Type, StreamCodec and handler. PayloadConnection.play produces RegistryFriendlyByteBuf. This matches common packet shape and avoids the legacy SimpleChannel class discriminator requirement. ChannelBuilder.payloadChannel constructs the public builder; PayloadChannel itself is package-private, so store the returned built Channel<CustomPacketPayload>, not its implementation class. [1.21.1 PayloadChannel](https://github.com/MinecraftForge/MinecraftForge/blob/1.21.1/src/main/java/net/minecraftforge/network/PayloadChannel.java#L106), [1.21.1 play buffer](https://github.com/MinecraftForge/MinecraftForge/blob/1.21.1/src/main/java/net/minecraftforge/network/payload/PayloadConnection.java#L100), [26.1.2 builder](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/src/main/java/net/minecraftforge/network/ChannelBuilder.java#L198), [26.1.2 PayloadChannel](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/src/main/java/net/minecraftforge/network/PayloadChannel.java#L106).
- PayloadFlow.add handlers execute on the network thread; addMain enqueues and marks handled. With `add`, the Forge context wrapper should delegate enqueueWork to Forge's Context and mark handled after dispatch. With addMain, avoid a second queue by letting wrapper enqueueWork execute inline on the already selected main thread. Pick one contract and test it. [PayloadFlow](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/src/main/java/net/minecraftforge/network/payload/PayloadFlow.java), [receive dispatch](https://github.com/MinecraftForge/MinecraftForge/blob/1.21.1/src/main/java/net/minecraftforge/network/PayloadChannel.java#L189).
- Channel.send invokes the registered codec and validates protocol/direction, whereas direct connection.send(new ClientboundCustomPayloadPacket(customRecord)) bypasses this channel encoder. The common source currently uses direct vanilla sends throughout packet helpers, clients, server managers and scenes. Add an @ExpectPlatform transport abstraction (sendToPlayer/sendToServer/broadcast as necessary), preserve vanilla sends in Fabric/NeoForge adapters, and use Forge Channel.send in Forge. Do not assume packet registration makes direct sends work. [Forge Channel](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/src/main/java/net/minecraftforge/network/Channel.java#L53), [quest direct send](../../common/src/main/java/grill24/fishtastic/network/QuestSyncPacket.java:116), [ambient direct send](../../common/src/main/java/grill24/fishtastic/client/ambient/AmbientContextClient.java:261), [1.20.1 transport reference](D:/GitHub/fishtastic-worktrees/mc-1.20.1/forge/src/main/java/grill24/fishtastic/network/forge/NetworkApiSidedImpl.java).
- Full direct-send review must include packet helpers for Quest/Tutorial/Encyclopedia/CosmeticCapture/config toggles, Bond/Rename/TakePile/RequestLeaderboard responses; server FishingMinigameManager/AmbientContextServer/CompanionSceneManager; client screens, tutorial handlers, CompanionBondInput, FishtasticKeyBinds, FishingMinigameClientHandler, AmbientContextClient; development RenderSelfTest sends. A simple `rg 'ClientboundCustomPayloadPacket|ServerboundCustomPayloadPacket' common/src` gives the concrete inventory. [server minigame](../../common/src/main/java/grill24/fishtastic/server/FishingMinigameManager.java:1156), [scene](../../common/src/main/java/grill24/fishtastic/server/CompanionSceneManager.java:214), [screens](../../common/src/main/java/grill24/fishtastic/client/CompanionScreen.java:78), [selftest](../../common/src/main/java/grill24/fishtastic/client/selftest/RenderSelfTest.java).
- ChannelBuilder uses integer networkProtocolVersion, exact by default; optional explicitly permits missing/vanilla peers. Existing NeoForge optional status is not sufficient reason to permit absent clients on Forge, given required custom content and synced datapack registries. Decide strict same-protocol connection policy explicitly and document it. Cross-loader wire interoperability is not established. [ChannelBuilder policy](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/src/main/java/net/minecraftforge/network/ChannelBuilder.java#L49).
- Fallback if payload API in pinned Forge artifacts differs: SimpleChannel supports StreamCodec and RegistryFriendlyByteBuf directions in both reviewed branches, but runtime class dispatch means each registration needs a concrete Class<T> or a typed envelope with a stable ID/codec table. Add explicit payloadClass to common registration declarations and thin adapters if using class dispatch; do not cast CustomPacketPayload.class for all messages. An envelope adds a protocol surface and should remain second choice. The 1.20.1 custom BufCodec/FishtasticPayload layer solves older APIs and is unnecessary by default for 1.21.1+. [1.21.1 SimpleChannel](https://github.com/MinecraftForge/MinecraftForge/blob/1.21.1/src/main/java/net/minecraftforge/network/SimpleChannel.java#L59), [26.1.2 SimpleChannel](https://github.com/MinecraftForge/MinecraftForge/blob/26.1.2/src/main/java/net/minecraftforge/network/SimpleChannel.java), [1.20.1 implementation](D:/GitHub/fishtastic-worktrees/mc-1.20.1/forge/src/main/java/grill24/fishtastic/architectury/forge/ForgePacketRegistrar.java).

### Inferences

- Prefer the existing 1.20.1 event-scoped real-holder strategy for the first Forge registration prototype, adapted to data components and version-specific APIs. Reassess if pinned modern Forge provides a simpler genuine deferred Holder without violating common behavior.
- Prefer Forge-owned SavedData plus explicit sync behind the existing storage facade for both versions. Capability-backed player persistence is an alternative, but adds clone/tracking/invalidation mechanics. Neither design implies automatic save compatibility with NeoForge attachment NBT; loader-switch save migration is an explicit separate decision.
- PayloadChannel prototype can avoid altering every packet registration. Exact Java wildcard adaptation between common `? super RegistryFriendlyByteBuf` and Forge `StreamCodec<BUF,MSG>` should be resolved with a bounded codec adapter, not unsafe broad raw casts.
- Connect only after registry synchronization completes; every registry-bearing ItemStack payload must use the active connection's registry buffer. Never create RegistryFriendlyByteBuf with an empty/global registry lookup to satisfy the generic type.

### Gaps

- Exact DataPackRegistryEvent/registration API on pinned Forge 26.1.2 was not successfully fetched; use pinned source and compile before promising the NeoForge signature unchanged. Same caveat applies to STARTUP config equivalent, modern Forge companion capabilities and loader classloading hooks.
- Reviewed GitHub version branches are moving heads. Pin artifact versions and compare their extracted source before implementation; no payload prototype has been compiled.
- Cross-loader save migration, cross-loader multiplayer and optional absent-peer support need explicit scope decisions. Recommended initial acceptance is same-version Forge client/server with required Fishtastic and Gelatin UI.

### Inferences

Recommended work packages and exit criteria for each Minecraft version:

1. **Loader service skeleton and side isolation.** Implement every listed @ExpectPlatform target, commands, event hooks and config path resolution. Final jar must contain transformed common and fishsim runtime classes, no dev harness/MCP runtime requirements, no unresolved Fabric/NeoForge annotations. Launch dedicated server before client polish to catch server references to Minecraft/client model classes.
2. **Registration and registry proof.** Implement all nine static/seven datapack registries with real holders. Exercise item/block equality, creative tabs, data-component defaults and network-synchronized components, menu factories, recipes, block entity construction, dispenser behavior. Invalid references must fail loading clearly. Add a small custom datapack override to prove client synchronization on join and `/reload`.
3. **Transport prototype.** Start PayloadChannel with one C2S packet and one registry-bearing S2C ItemStack packet; prove main-thread handler, sender resolution, typed ID, exact version check and direction rejection on dedicated client/server. Then route every direct send through the transport abstraction and register all 36 common payloads. Include codec-only Fabric registration regression. Test oversized/stale/duplicate fishing results, forged menu IDs, invalid slots/species/names and unloaded tank positions using existing validation logic.
4. **Persistence and companion sync.** Add SavedData-backed Forge storage or prove capability alternative; explicit owner and watcher sync, empty-party removals, late join, re-track, dimension change, death/respawn, logout/rejoin, restart, changed world.
