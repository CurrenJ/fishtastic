# Gelatin UI prerequisite, validation, and release

## What must the Gelatin UI Forge prerequisite preserve?

### Takeaway
Add Forge to both target Gelatin branches before integrating Fishtastic. Preserve the complete common library and its public API; the platform seam is small, but menu lifecycle ordering and 26.1.2 GUI rendering require explicit proof gates.

### Cited Findings
- Both target settings include common, Fabric, NeoForge only. Both use Gelatin version 1.0.37, published with Minecraft suffix; target dependencies are Fabric API 0.145.4+26.1.2/NeoForge 26.1.2.4-beta and Fabric API 0.116.7+1.21.1/NeoForge 21.1.209. These are inspected source properties, not proposed upgrade pins. — [26.1.2 properties](D:/GitHub/gelatin-ui/gradle.properties:8), [1.21.1 properties](D:/GitHub/gelatin-ui-worktrees/mc-1.21.1/gradle.properties:10), [settings](D:/GitHub/gelatin-ui/settings.gradle:16).
- The platform bridge is `SidedRegistrationHelper.getMenuRegistrationHandler()` using `@ExpectPlatform`; the actual handler must create/store a `MenuType<GelatinMenu>` during deferred registration. Existing 1.20.1 Forge supplies exactly this seam. Preserve package names and all common API signatures so consumers keep their imports. — [bridge](D:/GitHub/gelatin-ui/common/src/main/java/io/github/currenj/gelatinui/registration/menu/SidedRegistrationHelper.java:5), [NeoForge handler](D:/GitHub/gelatin-ui/neoforge/src/main/java/io/github/currenj/gelatinui/registration/menu/neoforge/MenuRegistrationHandlerNeoForge.java:11), [Forge reference](D:/GitHub/gelatin-ui-worktrees/mc-1.20.1/forge/src/main/java/io/github/currenj/gelatinui/registration/menu/forge/MenuRegistrationHandlerForge.java:11).
- Important lifecycle mismatch: both target `GelatinUi.init()` implementations register examples then immediately fire the menu event, whereas 1.20.1 explicitly separates `init()` from `fireMenuRegistrationEvent()`. Its Forge implementation delays firing to MENU RegisterEvent before the handler DeferredRegister's listener, explaining that dependent mod constructor ordering otherwise silently skips menus and produces null MenuTypes during screen registration. — [26.1.2 early fire](D:/GitHub/gelatin-ui/common/src/main/java/io/github/currenj/gelatinui/GelatinUi.java:15), [1.21.1 early fire](D:/GitHub/gelatin-ui-worktrees/mc-1.21.1/common/src/main/java/io/github/currenj/gelatinui/GelatinUi.java:15), [common split](D:/GitHub/gelatin-ui-worktrees/mc-1.20.1/common/src/main/java/io/github/currenj/gelatinui/GelatinUi.java:19), [race rationale and implementation](D:/GitHub/gelatin-ui-worktrees/mc-1.20.1/forge/src/main/java/io/github/currenj/gelatinui/forge/GelatinUiModForge.java:35).
- Fishtastic adds menu listeners for `fishtastic`, `leaderboard`, `quest_log`, `fish_encyclopedia`; screen listeners later resolve these IDs. Gelatin's screen resolver dereferences the map during apply, so a library-only title-screen test would miss the downstream race. — [consumer menus](D:/GitHub/fishtastic/common/src/main/java/grill24/fishtastic/compat/GelatinMenus.java:14), [consumer screens](D:/GitHub/fishtastic/common/src/main/java/grill24/fishtastic/compat/GelatinScreens.java:16), [resolver](D:/GitHub/gelatin-ui/common/src/main/java/io/github/currenj/gelatinui/registration/menu/ScreenRegistration.java:61).
- Forge's 1.21.x official guidance registers menu screens through `FMLClientSetupEvent.enqueueWork(MenuScreens::register)` because the screen map is not thread safe. The existing 1.20.1 Forge adapter follows that pattern; do not copy NeoForge's RegisterMenuScreensEvent blindly. — [Forge docs](https://docs.minecraftforge.net/en/1.21.x/gui/screens/), [existing adapter](D:/GitHub/gelatin-ui-worktrees/mc-1.20.1/forge/src/main/java/io/github/currenj/gelatinui/forge/GelatinUiModForgeClient.java:19).
- Gelatin opens menus through vanilla `ServerPlayer.openMenu(SimpleMenuProvider)` without extra buffer data. Official Forge docs support this model. Inspection found unused NeoForge payload imports, but no custom payload declarations or channel implementation in Gelatin's common/NeoForge source; do not invent a library packet channel. Fishtastic's own request/response packets remain its responsibility. — [open method](D:/GitHub/gelatin-ui/common/src/main/java/io/github/currenj/gelatinui/registration/menu/MenuRegistration.java:71), [Forge menus](https://docs.minecraftforge.net/en/1.21.x/gui/menus/), [library entry](D:/GitHub/gelatin-ui/neoforge/src/main/java/io/github/currenj/gelatinui/neoforge/GelatinUiModNeoForge.java:21), [consumer open synchronization](D:/GitHub/fishtastic/common/src/main/java/grill24/fishtastic/compat/GelatinOpenMenuCompat.java:53).
- Both target AT files change `HoverEvent$Action.UNSAFE_CODEC` and `CODEC` to public/nonfinal. 1.21.1 mixins include GuiGraphicsMixin client-side and HoverEventActionMixin common-side (JAVA_21). 26.1.2 NeoForge config includes GuiGraphicsMixin and GuiRendererMixin client-side (JAVA_25). Preserve tooltip factories and tooltip/chat codecs on client AND dedicated server. — [AT](D:/GitHub/gelatin-ui/neoforge/src/main/resources/META-INF/accesstransformer.cfg:1), [1.21.1 mixins](D:/GitHub/gelatin-ui-worktrees/mc-1.21.1/neoforge/src/main/resources/gelatinui-neoforge.mixins.json:1), [26.1.2 mixins](D:/GitHub/gelatin-ui/neoforge/src/main/resources/gelatinui-neoforge.mixins.json:1), [tooltip registration](D:/GitHub/gelatin-ui/neoforge/src/main/java/io/github/currenj/gelatinui/neoforge/GelatinUiModNeoForgeClient.java:29).
- 26.1.2 PiP behavior differs by loader: Fabric includes GameRendererMixin, adding a renderer instance to the vanilla GuiRenderer constructor list. NeoForge omits that mixin and registers a renderer factory with its PiP event because its patch changes the list element contract. The comment explicitly warns a raw instance causes a ClassCastException on NeoForge. — [constructor injection](D:/GitHub/gelatin-ui/common/src/main/java/io/github/currenj/gelatinui/mixin/GameRendererMixin.java:15), [Fabric config](D:/GitHub/gelatin-ui/fabric/src/main/resources/gelatinui-fabric.mixins.json:7), [NeoForge PiP](D:/GitHub/gelatin-ui/neoforge/src/main/java/io/github/currenj/gelatinui/neoforge/GelatinUiModNeoForgeClient.java:40).
- No PiP hook exists in the inspected 1.21.1 library adapter. HiResItems on 26.1.2 checks renderer registration and can decline rendering, so seeing ordinary items is insufficient proof of working high-resolution rendering. — [1.21.1 client](D:/GitHub/gelatin-ui-worktrees/mc-1.21.1/neoforge/src/main/java/io/github/currenj/gelatinui/neoforge/GelatinUiModNeoForgeClient.java:15), [HiResItems guard](D:/GitHub/gelatin-ui/common/src/main/java/io/github/currenj/gelatinui/gui/minecraft/hires/HiResItems.java:45).

### Inferences
- Implementation slices: build/module metadata and transformed common artifact; Forge menu-handler bridge; order-independent listener lifecycle; client screens/tooltips; 26.1.2 PiP integration; package/publication. Keep each reviewable and validate each with its consumers.
- First library gate must include a tiny external consumer or Fishtastic: register its listener during consumer construction, complete menu registry, assert all expected IDs resolve to registered non-null types exactly once, then apply screen factories and open a menu from the logical server. Exercise both listener-before-library-init and listener-after-library-init construction ordering in an isolated fixture. Do not settle for library examples alone.
- Port the 1.20.1 lifecycle concept, not its old event-bus syntax. Ensure the chosen Forge MENU callback precedes DeferredRegister processing; if current Forge ordering cannot guarantee that, register through a single controlled registry callback instead. Preserve public `init()` API semantics for existing consumers or introduce an explicit additive lifecycle method and migrate all loader entrypoints together. Regression-test Fabric/NeoForge event timing after any common change.
- PiP decision matrix: 1.21.1 = existing immediate GUI path, no new PiP subsystem; 26.1.2 Fabric = retain instance-list mixin; NeoForge = retain event factory; Forge = inspect pinned Forge GameRenderer/GuiRenderer patches, choose matching factory hook if present or a Forge-specific instance-list injection if signature remains vanilla. Never load both registrations. Verify renderer availability, enlarged item clarity, multiple distinct items per frame, clipping, reload, and resource disposal.
- The coordinator's build review establishes Loom 1.17 as a candidate supporting Forge 1.21.x/26.x. Pin and prove its compatible version for library and consumer together before runtime work; this note did not independently validate that build claim.

### Gaps
- No builds, game launches, or artifact resolution occurred in this research. Git metadata reads for all three Gelatin checkouts failed with permission denied; exact HEADs must be captured at implementation start. No escalation attempted solely for metadata.
- Forge 26.1.2 exact PiP hook availability remains unverified: direct raw event URLs failed and indexed GitHub directory content did not expose it. Do not state that Forge has NeoForge's event or that the Fabric injection will certainly work.
- JEI Forge coordinates/availability for both targets were not established in this scope. Treat optional integrations separately from the core launch gate and confirm primary Maven metadata before enabling them.

## What validation gates make the implementation trustworthy?

### Takeaway
Prove both development launches and packaged installation, then run existing assertions through a Forge adapter. Record fresh expected test names and counts from the pinned branch; historical pass counts are reference evidence only.

### Cited Findings
- Existing common GameTests are loader-neutral methods; per-loader registrations/testmod source sets expose them. The guide warns BUILD SUCCESSFUL can mean only an unrelated vanilla test ran if mod-class roots omit testmod. Forge registration must explicitly prove discovery. — [canonical guide](D:/GitHub/modding-guide/18-game-tests.md:1), [NeoForge source-set wiring](D:/GitHub/fishtastic/neoforge/build.gradle:28), [class-root explanation](D:/GitHub/fishtastic/neoforge/build.gradle:146).
- `gradle/gametest-world.gradle` creates a fresh UUID universe and deletes it only on success, retaining failed worlds. Reuse this behavior for Forge. — [fresh-world hook](D:/GitHub/fishtastic/gradle/gametest-world.gradle:1).
- `docs/run-pre-backport-validation.ps1` currently enumerates only Fabric/NeoForge, builds first, runs scenes in isolated worlds, checks PASS/FAIL labels, exactly one completion, expected scene prefixes, and process exit code. The two-client script also rejects any loader outside Fabric/NeoForge and assigns ports 25600/25601. Both need explicit Forge extension rather than assumed compatibility. — [validation](D:/GitHub/fishtastic/docs/run-pre-backport-validation.ps1:22), [assertion criteria](D:/GitHub/fishtastic/docs/run-pre-backport-validation.ps1:55), [loader validation](D:/GitHub/fishtastic/docs/fish-companions-twoclient/twoclient.init.gradle:16).
- Production jars exclude MCP bridge, simulation harness/viewer/render, and client selftest classes. Existing packaging verifier checks dev-class exclusion, MoodPresets presence, and dangling references but only visits Fabric/NeoForge. — [exclusions](D:/GitHub/fishtastic/neoforge/build.gradle:108), [packaging check](D:/GitHub/fishtastic/docs/check-cleanup-packaging.ps1:8).
- The pre-commit hook runs unit/sim/tank-shape tests and Fabric GameTests, explicitly skips NeoForge GameTests due to intermittent hangs; a green commit hook is not full loader validation. — [hook](D:/GitHub/fishtastic/scripts/git-hooks/pre-commit:1).
- Fabric remains the canonical datagen entry in `scripts/run_datagen.bat`, followed by registry JSON sync into common resources. Adding a loader must not create competing committed asset copies. — [script](D:/GitHub/fishtastic/scripts/run_datagen.bat:4).
- Historical 2026-10-15 evidence reports common 858 passed/1 skipped, fishsim 497 passed/59 skipped, and NeoForge 115/115 companion world/particle/mood/cost client checks. Those are historical, not fresh results or hardcoded expectations for the upcoming port. — [evidence](D:/GitHub/fishtastic/docs/fish-companions-world-validation.md:29).

### Inferences
- Gate V0: capture commits, dirty state, Java/Gradle/Loom/Forge/Gelatin versions; assemble unchanged baseline and store logs separately per MC/loader. Preserve existing backport progress as context, not a new-loader progress ledger. Inventory current branch test names/counts because parity work is moving.
- Gate V1: library JUnit/API checks plus representative consumer registration, tooltip codec, menus, inputs, scroll/clipping, item render and resource reload. Library alone and library+consumer must launch dedicated server without client-class resolution failures.
- Gate V2: run `:common:test`, `:fishsim:test`, tank-shape generator tests as present on that branch; compile all main/testmod source sets; add Forge GameTest wrapper equivalent to branch's actual test registry. Assert expected namespaces/test IDs, required count, report content and completion, not only task success. Run twice with fresh universes to expose state leakage. Use bounded watchdogs; retain failed worlds/logs/thread dumps.
- Gate V3: Forge isolated client scenes covering fishing/minigame HUD, quality item rendering, tank shapes/connections, water/glass/light/translucency, cosmetics, GUI menus, quests/tutorials, ambient population/water/lifecycle and companions. Extend exact script loader lists and give Forge its own port/run directories. Never run compiles/tests while clients hold shared development outputs.
- Gate V4: dedicated server plus two Forge clients, each distinct identity; verify initial login, tracking/late join, changing dimensions, death/respawn, reconnect, owner/nonowner companion party visibility, updates/removal, no duplicate entities/scenes, GUI request/response correctness, forged/invalid requests rejected through shared validation, disconnect cleanup, server restart/save-reload of progression/tanks/companions. A packet round-trip or storage codec unit test cannot replace this lifecycle check.
- Gate V5: clean installed Forge client/server using only production Fishtastic and matching Gelatin jars, expected required libraries, no IDE classpath/MavenLocal leakage. Validate manifest, mods.toml expansion and precise game/loader/Java ranges, mixins/AT and transformed ExpectPlatform methods, packet IDs/registration coverage, no testmod/MCP/selftest/dev simulation packages or dangling references, required fishsim runtime included. Smoke join/menu/fishing/tank/save/reload using production jars. Development scene harness is intentionally excluded, so use a separate testmod or explicit production smoke procedure.
- Gate V6: run Fabric/NeoForge regressions for every changed shared/build surface on both target versions; run existing 1.20.1 Fabric/Forge regression checks if release aggregation/tooling touches it. Test optional JEI separately both absent and present once availability is verified. Datagen proof is a clean generation/sync diff with all production content retained, not a requirement to duplicate providers unnecessarily.
- Completion evidence directory should contain pinned source manifest, resolved dependency manifest, task logs/JUnit reports, expected/discovered test inventory, scene summary/screenshots, production jar SHA256/listing, client/server/two-client logs, persistence results, and explicit remaining deviations. Mark interrupted runs unverified.

### Gaps

- Profile deployment is not yet part of this task. If later requested, use the profile-sync skill and create isolated Forge test profiles with correctly matched library jars; do not overwrite personal worlds/profiles to satisfy validation.

## How should releases and ongoing maintenance work?

### Takeaway
Release validated Gelatin Forge dependencies first, then build and release Fishtastic against resolvable published versions. The Fishtastic support matrix grows from six artifacts to eight: three loaders each on 26.1.2/1.21.1, plus unchanged Fabric/Forge on 1.20.1.

### Cited Findings
- Gelatin currently publishes Maven components with source/javadoc/signatures and Central bundle aggregation; its 26.1.2 platform output redirects components.java to the shadow jar. CurseForge publishing explicitly lists Fabric/NeoForge and Java 25. New Forge must participate with its actual production artifact, not raw/dev-shadow output. — [publication](D:/GitHub/gelatin-ui/build.gradle:61), [Central aggregation](D:/GitHub/gelatin-ui/build.gradle:185), [platform outgoing artifact](D:/GitHub/gelatin-ui/neoforge/build.gradle:65), [CurseForge](D:/GitHub/gelatin-ui/build.gradle:111).
- Existing 1.20.1 Forge library uses shadow+remapJar and explicit mixin config registration, demonstrating why artifact selection/mixin activation is version-specific. Do not copy NeoForge's metadata table assuming Forge reads it. — [Forge build](D:/GitHub/gelatin-ui-worktrees/mc-1.20.1/forge/build.gradle:64), [mixin activation](D:/GitHub/gelatin-ui-worktrees/mc-1.20.1/forge/build.gradle:80).
- Fishtastic CurseForge publishing has explicit loader uploads, Gelatin requirement, Java tagging and build dependencies for Fabric/NeoForge only. Common tests depend on gelatinui-common; NeoForge depends on gelatinui-neoforge. Forge therefore needs its matching gelatinui-forge coordinate and upload/dependency entry. — [Fishtastic publication](D:/GitHub/fishtastic/build.gradle:124), [common test dependency](D:/GitHub/fishtastic/common/build.gradle:29), [platform library dependency](D:/GitHub/fishtastic/neoforge/build.gradle:46).

### Inferences
- Dependency order: implement/publish-to-local Gelatin common and all affected loader artifacts under a new version; integrate Fishtastic using that exact version; validate isolated production installs; stage Gelatin Central/CurseForge releases; verify remote artifact resolution from clean consumer environment; then stage Fishtastic releases and exact Gelatin dependency. External publishing is subsequent implementation/release work, not authorized or executed by this research task.
- Add Forge to both repositories' settings/enabled-platforms and publication task dependencies. Keep artifact IDs loader-specific (`gelatinui-forge`, `fishtastic-forge`), Java 21/25 tags version-specific, and game version ranges bounded to the tested line. Include new Forge source/javadoc and signing tasks in Central aggregation as applicable.
- Acceptance matrix: 26.1.2 Fabric/NeoForge/Forge; 1.21.1 Fabric/NeoForge/Forge; 1.20.1 Fabric/Forge. Require both new Forge artifacts and regressions on the four existing target-version artifacts; preserve the two 1.20.1 artifacts. Eight is Fishtastic deliverable count, not a claim that every artifact must receive unrelated product changes.
- Maintain one Forge support implementation ledger separate from ongoing backport parity ledger; record exact pending action/evidence path, green gates and deviations. Shared gameplay and packet contracts stay common; loader adapters own event/rendering/storage mechanics. Keep loader-specific render hooks explicit to avoid growing conditionals throughout common UI.

### Gaps
- Current Gelatin published remote versions, publishing credentials, CurseForge Forge release availability and Central resolution were not tested. Fresh release numbers and minimum supported Forge versions must be selected after the toolchain prototype, not inferred from mutable latest versions.
