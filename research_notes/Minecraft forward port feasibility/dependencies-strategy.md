## What build and dependency work is actually required?

### Takeaway

Two Minecraft lines mean four new Fishtastic runtime artifacts for Fabric/NeoForge, or six if Forge passes its own acceptance gates, with matching separately distributed Gelatin UI artifacts. Preserve the current multiloader structure per version; no runtime Architectury API port is required by the inspected source.

### Inferences

- Recommended future default: dedicated 26.2 and 26.3 branches/worktrees for both Fishtastic and Gelatin after selecting clean baselines. Keep common within each Minecraft line and native loader adapters; port 26.2 first, then bring reviewed 26.2 changes to 26.3. Probe 26.3 toolchain and rendering early so sequential delivery does not hide a late blocker.
- Property-only switching is not credible as the release plan: hardcoded integration coordinates, version-dependent Java/API source, loader hooks, mixins, data/resource schemas and independent compatibility evidence remain. A single source tree with version adapters is a later option if measured diffs stay small; introducing a new preprocessor/multiversion framework during both ports adds independent migration cost.
- Native Fabric Loom/NeoForge ModDevGradle/ForgeGradle builds are fallback feasibility probes if Architectury Loom fails on a target, not the initial migration. A replacement must recreate ExpectPlatform transforms, annotation remapping, access conversion, shaded common, fishsim, runs, tests and release metadata. Budget it as a distinct architecture decision, not a dependency bump.

### Gaps

- No target compile or launch was authorized/performed, so all source compatibility remains unproven.
- Exact local sibling clean commit/dirty patch inventories and full dependency graphs must be captured at kickoff; the current feature baseline includes ongoing Forge edits and other work.
- Final distributed jars were not inspected in this audit; source packaging declarations show intent, not proof of actual jar contents.

## What should the future execution plan, effort, and maintenance contract be?

### Takeaway

Keep version and loader gates independent, with a clean baseline, small reproducible build probes, Gelatin-first rendering validation, then consumer work and installed distribution proof. Estimates below are planning judgments for experienced maintainers, not measured throughput or promises.

### Cited Findings

- Existing current-line Forge work has already caught production-only missing selftest references, a dedicated-server LocalPlayer class-loading problem, packet handled flags, duplicate mod/resource roots, incorrect Mixin Java compatibility, wrong-Minecraft Gelatin acceptance and test discovery traps. This concretely supports early installed client/server and negative metadata checks on each target rather than postponing them to release week. [Latest Forge checkpoints](D:/GitHub/fishtastic/docs/forge-support-progress.md), [Forge packaging](D:/GitHub/fishtastic/forge/build.gradle).
- Existing branches isolate older Minecraft lines and the active root26.1.2 line, according to the read-only worktree inventory supplied to the coordinator; root source has Minecraft-free fishsim and tools boundaries suitable for preserving across forward ports. [Settings](D:/GitHub/fishtastic/settings.gradle), [fishsim build](D:/GitHub/fishtastic/fishsim/build.gradle).

A whole-product forecast should be wider and driven by the separate subsystem audit; no defensible fixed total exists until D01 and the first render/menu prototypes. If a loader toolchain fails a2-day focused proof, reassess candidate upgrade/native build fallback or defer that loader instead of estimating adapter work atop an unknown build.

Critical path: D00 -> D01 -> Gelatin target render/menu prototype -> Fishtastic most invasive render prototype -> complete subsystem port -> D05 -> D08. 26.3 toolchain/render probes run early; full26.3 delivery can follow reviewed26.2. Optional Forge may proceed on its own lane once its baseline is reviewed; it should not silently broaden the first Fabric/NeoForge commitment.

Release and rollback contract:

1. Each advertised Minecraft+loader cell needs its own final jar, Gelatin dependency, clean launch and acceptance evidence. A green26.2Fabric cell says nothing about26.3NeoForge or Forge.
2. Keep baseline26.1.2 support intact. Carry shared fixes as reviewable small commits with a feature/change ledger; verify originating and target branch tests for later bugfix propagation. Never advance backport parity markers for forward-port work.
3. Use disposable copies of representative worlds. Take original save backups before any vanilla version upgrade. World upgrade and mod save migration are one-way until proven otherwise; rollback means restoring the original version plus original world backup, not opening a new-version save in an older game.
4. Publish Gelatin dependency first, wait for public repository/index visibility, then release only cells that clean-cache resolve it. Consumer metadata must bound Minecraft correctly; reject wrong-line Gelatin early. Keep protocol equality and loader-switch compatibility scoped to actual tests.
5. First target release should be explicitly tagged beta while installed acceptance and user feedback mature; use unique beta version strings so release fingerprints cannot be confused.
6. Current publication task assumes exactly two loaders. Refactor only as future authorized implementation to explicit validated cells rather than blindly uploading every configured module. Preserve safe missing-secret failures; do not expose credential files in evidence.
7. Keep ignored transient logs under a dedicated future build/forward-ports/<version>/<loader>/<gate> tree, plus tracked concise progress/index records with pinned commits, commands, exit codes, discovered test counts, artifact hashes, screenshot indexes and next pending operation. Interrupted runs remain unverified.

Maintenance planning: four new release cells imply at least4 installed client/server combinations per release, plus matching dependency library builds; optional Forge adds2 more. Maintain a per-version change ledger and fix-origin policy, not unreviewed blanket cherry-picks. Budget roughly0.5-1.5 engineer days per routine synchronized release for extra build/test/packaging triage across four cells, and1-3 days for API/loader-breaking updates, with optional Forge adding separate triage. These are explicit planning assumptions to replace with measured first-release timings. Preserve shared fishsim tests and source equivalence so version maintenance does not fork the engine unnecessarily. A new multiversion build framework should only be considered if measured repeated merge/testing costs exceed its migration cost.

### Gaps

- Estimates cannot predict rendering redesign, native GPU backend issues, library rewrites, or upstream loader bugs before probes.
- Required operating-system/GPU breadth, release cadence, target patch-version policy, and whether Forge must ship concurrently are product decisions; initial plan can preserve Fabric/NeoForge as the default verified matrix and mark Forge conditional.
- No current source compile/runtime capability claim for26.2 or26.3 is justified by this research. Future implementation must gather execution evidence.
