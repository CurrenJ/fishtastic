# Fishtastic forward-port source exposure and validation audit

## What parts of the current source create concrete 26.2 and 26.3 port work?

### Takeaway
26.2 has definite GUI and Fabric datagen migration work; 26.3 adds definite native input, GPU API, shader, and outline-atlas redesign work. Source breadth is substantial, but file inventory measures audit surface, not a claim that every class needs modification. This is a read-only assessment of the 2026-10-19 working tree on branch `26.1.2`, supplied HEAD `0b84e7e327e9317ebd77c6fb61d418bb33329cdf`; no compilation or runtime compatibility has been established.

### Cited Findings
- Common has 415 main Java files; Fabric 39, NeoForge 25, Forge 20. Common mixin configuration enables 25 client entries and 5 shared entries, all required with defaultRequire=1. Fabric and NeoForge extra configs are empty. These are live-tree counts obtained with `rg --files <module>/src/main/java -g '*.java'` and PowerShell `Measure-Object`; mixin counts come from parsing the JSON. [Common mixins](../../common/src/main/resources/fishtastic.mixins.json:1).
- **26.2 / proven, high confidence:** `Minecraft.screen` / `setScreen` migrate to dedicated GUI access; 10 main Java files reference the old forms, including FishtasticKeyBinds:65-97; QuestLogScreen:294,314; FishEncyclopediaScreen:200; tutorial handlers; and selftest harness. The migration affects opening/closing screens, HUD suppression, input gating and tests, not merely imports. [Fabric 26.2](https://fabricmc.net/2026/06/15/262.html); [Key bindings](../../common/src/main/java/grill24/fishtastic/client/FishtasticKeyBinds.java:65).
- **26.2 / proven, high confidence:** `valueLookupBuilder` is removed. Exactly two provider files use it: Fabric FishtasticBlockTagProvider:26,29 and FishtasticItemTagProvider:51-307. Blocks and items become key-oriented datagen inputs via BlockIds, BlockItemIds and ItemIds. Audit all recipe/model/loot/tag builders; avoid assuming registration itself must be completely rewritten. [Fabric 26.2](https://fabricmc.net/2026/06/15/262.html); [Block tags](../../fabric/src/main/java/grill24/fishtastic/fabric/datagen/FishtasticBlockTagProvider.java:26); [Item tags](../../fabric/src/main/java/grill24/fishtastic/fabric/datagen/FishtasticItemTagProvider.java:51).
- **26.3 / proven, highest risk:** FishtasticItemOutlineAtlas directly sets `RenderSystem.outputColorTextureOverride` and `outputDepthTextureOverride` at 350-351 and 417-418 and clears them at 373-374 and 428-429. Both globals are removed; target design requires explicit RenderPass attachments and prepared feature frames. This is a rendering control-flow redesign, not only renamed imports. Preserve atlas slot lifetime, padding, mask composition, per-frame animation, projection state and render-thread ordering. [26.3 primer, No More Texture Override Shenanigans](https://docs.neoforged.net/primer/docs/26.3/#no-more-texture-override-shenanigans); [Atlas](../../common/src/main/java/grill24/fishtastic/client/renderer/FishtasticItemOutlineAtlas.java:350).
- **26.3 / proven broad exposure:** 39 main Java files import `com.mojang.blaze3d`; primer says rendering APIs move to `com.mojang.renderpearl` with API/frontend/backend separation. Do not blindly rename every Blaze3D package: input/platform pieces require separate mapping. Audit FishtasticRenderPipelines:34,131,147,181,217,260,292,307; all effect UBO classes; outline atlas; GuiRendererExecuteDrawMixin; RenderTypeMixin; RenderBuffersMixin; screenshot GPU readback in RenderSelfTest:7137-7141. [26.3 primer, Renderpearl](https://docs.neoforged.net/primer/docs/26.3/#renderpearl); [Pipelines](../../common/src/main/java/grill24/fishtastic/client/renderer/FishtasticRenderPipelines.java:34).
- **26.3 / proven shader exposure:** 14 shader source files exist. `core/gui_item_outline.vsh` uses GLSL 330, hand-copied DynamicTransforms/Projection blocks, and unlocated `in`/`out` declarations at 14-20. Shaderc and explicit locations need mapping against target vanilla shaders; audit every vertex/fragment pair for locations, matching varyings, UBO layout and backend conventions. No active `#moj_import` directive was found, so its removal is not itself a proven direct blocker here. [26.3 primer, Shader Extensions and Layouts](https://docs.neoforged.net/primer/docs/26.3/#shader-extensions-and-layouts); [Outline vertex shader](../../common/src/main/resources/assets/fishtastic/shaders/core/gui_item_outline.vsh:1).
- **26.3 / proven native input break:** CompanionBondInput:15,38 imports GLFW and polls `glfwGetMouseButton(window.handle(), key.getValue())`; FishEncyclopediaScreen:62,229 compares GLFW Escape. SDL replaces GLFW and changes mouse/key codes. Replace native polling with target input facilities and audit key persistence/rebinding; do not hardcode integer codes. Gelatin custom text fields need SDL focus and preedit handling review even though that library is a separate repository. [Fabric 26.3 SDL](https://www.fabricmc.net/2026/09/15/263.html); [Bond input](../../common/src/main/java/grill24/fishtastic/client/CompanionBondInput.java:38); [Encyclopedia input](../../common/src/main/java/grill24/fishtastic/client/FishEncyclopediaScreen.java:229).
- **26.2/26.3 / exposure confirmed, exact break not proven:** 19 main files use GuiGraphicsExtractor. FishTankBlockEntityRenderer already splits `createRenderState` (277), `extractRenderState` (282) and `submit` (322), which is favorable, but its actual target contracts still need source comparisons. FishtasticWorldOutlineRenderer:46 builds a custom RenderType and :101 submits custom outline geometry; CompanionRender:186, CompanionFishPose:68, ClientCompanions:530, AmbientFishRuntime:1450 share submission infrastructure. [Tank renderer](../../common/src/main/java/grill24/fishtastic/client/renderer/FishTankBlockEntityRenderer.java:282); [World outline](../../common/src/main/java/grill24/fishtastic/client/renderer/FishtasticWorldOutlineRenderer.java:46); [Companions](../../common/src/main/java/grill24/fishtastic/client/companion/ClientCompanions.java:530).
- **Backend audit:** `rg -l org.lwjgl.opengl` found zero files in four main Java source roots. The existing use of Blaze3D is advantageous for Vulkan, but does not prove backend portability: target overrides, shader conventions and custom passes remain material. GLFW and LWJGL MemoryStack imports must not be mislabeled as raw OpenGL use. [Fabric Vulkan change](https://fabricmc.net/2026/06/15/262.html); [Atlas](../../common/src/main/java/grill24/fishtastic/client/renderer/FishtasticItemOutlineAtlas.java:5).
- **Exact mixin contracts to diff first:** GameRendererMixin:42 hardcodes render descriptor; GuiRendererMixin:46,79,119,162 targets submitBlitFromItemAtlas; GuiRendererExecuteDrawMixin:19 patches draw execution; ItemEntityRendererMixin:63,82 hardcodes submit descriptor; AvatarRendererMixin:27 hardcodes constructor; ItemInHandLayerMixin:58,80 targets submitArmWithItem call; RenderTypeMixin:29 redirects render internals. FishingHookMixin:53,75,126,135,175 targets retrieve/tick/catchingFish calls, fluid checks and particle emission, so server fishing semantics are also fragile. Required mixins should remain strict and be checked against target decompilation, not muted with require=0. [Game renderer](../../common/src/main/java/grill24/fishtastic/mixin/GameRendererMixin.java:42); [GUI renderer](../../common/src/main/java/grill24/fishtastic/mixin/GuiRendererMixin.java:46); [Fishing hook](../../common/src/main/java/grill24/fishtastic/mixin/FishingHookMixin.java:53).
- Six access-widener entries (one accessible field, two methods, three classes) include RenderType.create descriptor, ItemModels.ID_MAPPER, CreativeModeTab.Output, MenuScreens.ScreenConstructor and MenuType.MenuSupplier/constructor. Resolve each name and descriptor per target and verify generated platform access configuration. [Access widener](../../common/src/main/resources/fishtastic.accesswidener:1).
- Seven custom synchronized datapack registries register in Fabric FishtasticFabric:41-47 and NeoForge FishtasticNeoForge:89-103: item effects, fish profiles, temperaments, quests, shop entries, encyclopedia entries and cosmetics. 26.3 reworks reloadable registries and folds recipes/advancements into dynamic loading; whether each existing stable registry should become reloadable is a design decision, not automatic. Test reload behavior and cached holders together with client synchronization. [Fabric registration](../../fabric/src/main/java/grill24/fishtastic/fabric/FishtasticFabric.java:41); [NeoForge registration](../../neoforge/src/main/java/grill24/fishtastic/neoforge/FishtasticNeoForge.java:89); [Fabric dynamic registries](https://www.fabricmc.net/2026/09/15/263.html).
- MarineCompostRecipe extends CustomRecipe, exposes category MapCodec and StreamCodec, matches dirt + fish and preserves quality and pile remainder behavior. FishtasticRecipeSerializers:13 constructs `new RecipeSerializer<>(CODEC, STREAM_CODEC)`. Inspect target recipe/serializer contracts and complete JEI recipe integration, not just compile the recipe itself. ConstantValue.exactly appears in Fabric FishtasticBlockLootTableProvider:55 and needs review against 26.3 number-provider split. [Recipe](../../common/src/main/java/grill24/fishtastic/recipe/MarineCompostRecipe.java:31); [Serializer](../../common/src/main/java/grill24/fishtastic/recipe/FishtasticRecipeSerializers.java:13); [Loot provider](../../fabric/src/main/java/grill24/fishtastic/fabric/datagen/FishtasticBlockLootTableProvider.java:55); [26.3 recipe and number-provider context](https://www.fabricmc.net/2026/09/15/263.html).

### Inferences
- Rendering/library readiness is likely the critical path, especially 26.3 atlas and shaders. Vanilla-independent fishsim and much pure data/math logic should be retained unchanged unless tests expose target interaction issues.
- Sequence 26.2 as an independent stabilization point, then apply 26.3 delta to its verified baseline. Keep each target independently releasable; do not claim one binary supports both merely because Java compilation succeeds.
- Old modding guide references to 09-rendering.md are stale: that file does not exist. Read _research/fishtastic-findings.md and _research/gelatin-ui-findings.md as context, but target source and actual current tree win over historical snippets.

### Gaps
- No target source tree was compiled or inspected method by method; exact renderer callback signatures and loader event changes remain a future discovery task.
- No proof yet that target gelatin-ui, JEI, Iris/Oculus/Sodium equivalents implement the required APIs. Compatible library versions are an external gate.

## How do networking, save data and the dirty work affect the plan?

### Takeaway
The mod has clear platform seams, but multiplayer correctness and persistent data need explicit gates. The audit includes uncommitted Forge-related transport/cache work; its presence is not evidence of release readiness.

### Cited Findings
- FishtasticPackets registers 20 C2S payloads at lines 59-155 and 17 S2C payloads at 162-246; S2C codecs also have a separate server registration list at 257 onward. Require equal payload sets between handler and codec registrations and audit direction/thread boundaries per loader. PacketRoundTripGameTests:43 documents registry-aware buffers and ItemStack-specific equality. [Packet registry](../../common/src/main/java/grill24/fishtastic/network/FishtasticPackets.java:59); [Round trips](../../common/src/testmod/java/grill24/fishtastic/gametest/PacketRoundTripGameTests.java:43).
- `FishtasticTransport.java` is currently untracked. It centralizes vanilla custom payload sending with an installable Sender for Forge channels and imports client Minecraft in common source. VanillaSender.sendToServer uses Minecraft.getInstance/getConnection; dedicated-server classloading and side boundaries must be checked empirically, including packaged JAR boot, not inferred as already broken or safe. [Working-tree transport](../../common/src/main/java/grill24/fishtastic/network/FishtasticTransport.java:1).
- `CompanionPartyClientCache.java` is currently untracked. It holds a ConcurrentHashMap of UUID to CompanionParty, applies/removes parties and resets all entries; CompanionPartySyncPacket:34 enqueues cache application. CompanionParty:75-83 persists/streams item stacks. Forge additionally has CompanionPartySavedData, so cross-loader storage mechanisms differ. Acceptance needs owner/tracker sync, join/leave, respawn, dimension change, reconnect and cache clearing to avoid ghost parties. [Cache](../../common/src/main/java/grill24/fishtastic/companion/CompanionPartyClientCache.java:1); [Sync packet](../../common/src/main/java/grill24/fishtastic/network/CompanionPartySyncPacket.java:34); [Party codecs](../../common/src/main/java/grill24/fishtastic/companion/CompanionParty.java:75); [Forge persistence](../../forge/src/main/java/grill24/fishtastic/companion/forge/CompanionPartySavedData.java:23).
- FishTankBlockEntity saves through ValueOutput at 465 and loads ValueInput at 588, including registry block identifiers at 599-634, item stacks at 703 and cosmetic structure IDs at 770-779; missing structure lookup can skip entries. Its update tag/packet are at 825/831. Save-upgrade tests therefore must assert semantic counts and identifiers after reload, not merely absence of crash. [Tank persistence](../../common/src/main/java/grill24/fishtastic/blockentity/FishTankBlockEntity.java:465).
- FishCatchSavedData:197-224 codec includes per-player catches, quest state, cleanup goal and tutorials; :233 uses server DataStorage computeIfAbsent. PlayerQuestState:96-115 includes quest/lifetime maps and unlocked species. Preserve field names/defaults and verify old-save fixtures after upgrades. [Catch save](../../common/src/main/java/grill24/fishtastic/server/FishCatchSavedData.java:197); [Quest state](../../common/src/main/java/grill24/fishtastic/server/PlayerQuestState.java:96).

### Inferences
- Freeze a reviewed baseline commit including or excluding the uncommitted feature set before starting port implementation. Save a local inventory/diff and immutable fixture copy; do not port a moving working tree.
- Run installed dedicated-server tests on every intended loader. A development integrated server will not adequately prove absence of client class loading.
- Test 26.1.2 to 26.2 and 26.2 to 26.3 on separate copied worlds; additionally test direct 26.1.2 to 26.3 if advertised. Do not require downgrade compatibility unless intentionally designed and tested.

### Gaps
- No runtime evidence for transport/cache changes was obtained. They must not silently become the assumed known-good baseline.
- No exhaustive schema/codec compatibility diff or security audit of all packet validation was performed in this source exposure pass.

## What validation matrix and implementation gates should a future port require?

### Takeaway
There is substantial existing test infrastructure, but a test-discovery manifest and rendered/installed-client checks are essential: a green Gradle task alone cannot prove the port.

### Cited Findings
- Current source contains 48 common JUnit files, 107 fishsim JUnit files, 1 tank geometry test file and 37 shared testmod files. A raw `rg -n '@Test' common/src/test/java fishsim/src/test/java tools/tank-shape-gen/src/test/java` count is 666 annotation lines, and `rg -n 'static void [a-zA-Z].*GameTestHelper' common/src/testmod/java` counts 387 lines. These are source inventory counts, not discovered/executed tests: parameterization, helpers and loader wrappers change runtime totals. [Common test configuration](../../common/build.gradle:29); [fishsim build](../../fishsim/build.gradle:5); [Shared game tests](../../common/src/testmod/java/grill24/fishtastic/gametest/PacketRoundTripGameTests.java:43).
- Fabric gametest run is configured at fabric/build.gradle:161-167 with report path; NeoForge has explicit source-set discovery wiring at neoforge/build.gradle:146-155 and gametest run at 174-182. NeoForge test structure has datagen prerequisite. Check expected Fishtastic test names and nonzero namespace counts. [Fabric](../../fabric/build.gradle:161); [NeoForge](../../neoforge/build.gradle:146).
- RenderSelfTest:115-121 is marker-gated, emits `[selftest] CHECK ... PASS|FAIL` and screenshots; default scenes at 151 are tank, shapes, stress512, items, held, outline, fabulous, guiscale, fixes, hud, gizmos, pertank, highlight. Opt-in scenes include companionparty, twoclient, companionworld, ambientparity, ambientwater, ambientcontext, ambientpopulation, ambientlifecycle and ambientisland. Development harness is excluded from packaged jars at fabric/build.gradle:127-130 and neoforge/build.gradle:117-120. Thus development selftests and packaged-JAR validation are separate gates. [Selftest](../../common/src/main/java/grill24/fishtastic/client/selftest/RenderSelfTest.java:115); [Fabric exclusion](../../fabric/build.gradle:127).

### Inferences
Future implementation gate order, independently for each version:
1. Baseline lock: commit SHA + dirty diff disposition + dependency coordinates + Java/Gradle/loader pins + registry/content manifest + copied world fixtures + expected test IDs + baseline screenshots/performance. No implementation until approved scope starts.
2. Dependency/toolchain resolution: minimum empty loader project and gelatin-ui first, then all intended loader modules; compile common and testmod; transform/access-widener/mixin audit against exact target source descriptors.
3. Server core: registration ordering, all seven registries, codecs, components, recipes/loot/tags/datagen, saved-data loading and packet registration; clean dedicated boot then reload/stop/restart.
4. Renderer: extract/submit contracts; custom pipeline and UBO mapping; explicit atlas pass redesign for 26.3; shader layouts; resize/reload resource lifetime; feature ordering. Pass stock renderer before optional shader integration.
5. UI/input: dedicated GUI/HUD routing, key bindings and mouse state, focus/IME/preedit for custom text widgets, scrolling/tooltips/modal behavior; migrate harness itself before trusting it.
6. Multiplayer and save upgrades: owner/tracker behavior, auth-sensitive packet actions, all party and catch data, reconnect and dimension transitions; repeat on packaged JARs.
7. Release verification: full intended matrix with deterministic artifacts, no silent test skips, no required mixin warnings, accepted screenshot differences, known limitations and dependency constraints documented.

Proposed acceptance matrix (every target × every explicitly supported loader; Forge is a separate optional lane until platform feasibility is verified):
