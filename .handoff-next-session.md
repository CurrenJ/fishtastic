- Pre-commit hook's compile stage is fast and reliable; the actual `git commit` write step
  intermittently fails with "1Password: failed to fill whole buffer" or "1Password: agent returned
  an error" (GPG signing via 1Password) — just retry the same commit command. This session it took
  4 retries in a row before succeeding once; if it fails many times in a row, it may need the 1Password
  app itself checked (unlocked, agent restarted) rather than blind retries.
- `:fabric:runDatagen` boots a real Fabric mod loader instance and writes generated output straight
  into `common/src/main/resources` via `copyGeneratedAssetsToCommon` — even on a FAILED run, partial
  output gets copied. It also rewrites every touched file's line endings, so a failed/successful run
  can make `git status` show thousands of false "modified" files that are pure CRLF churn. Always
  check `git -c core.autocrlf=false diff --stat` (or `--ignore-all-space`) before trusting `git
  status`'s count.
- `System.out.println`/log4j INFO lines from inside a forked datagen/gametest JVM don't reliably
  reach Gradle's captured stdout — write to a file instead, or read the run's own log file directly
  (e.g. `forge/build/gametest/logs/latest.log`/`debug.log`, `fabric/build/gametest/logs/...`) rather
  than trusting Gradle's piped console output. This bit twice this session: both `:forge:runData`'s
  JEI crash and `:forge:runGametest`'s pass/fail summary only showed up in the run's own log file,
  not Gradle's stdout.
- Verify signatures against real jars/sources via `javap`, not memory. Jar paths used this session
  (still current) are listed at the bottom of this file.
- **New this session**: a Forge `runs {}` block that only calls `forgeTemplate("data")` (or any
  template) without also calling `environment(...)` explicitly will crash Gradle at configuration
  time with `MissingValueException: ... 'runtimeEnvironment'` — the template only sets that property
  lazily, inside the run task's own execution, but Gradle reads it eagerly while building the task
  graph. Always pair `forgeTemplate(...)` with an explicit `environment(...)` call (see
  `forge/build.gradle`'s `data`/`gametest` blocks for the pattern).
- **New this session**: if a headless Forge run (`runData`, `runGametest`, etc.) appears to hang with
  no further log output, check with `jstack` (JDK 21's jstack attaches fine to a JDK 17 target)
  before assuming it's still working — if `main` is gone and only non-daemon FML worker-pool threads
  remain "waiting on condition", the JVM has already finished (or crashed) and just isn't exiting.
  Two distinct causes hit this session: an uncaught exception killing `main` silently (B6.1's
  original gametest hang; this session's JEI-in-Forge-datagen crash was the same shape), and — new,
  unfixed — Forge's `DatagenModLoader` apparently never shutting down its worker-pool executors when
  a mod registers **zero** `GatherDataEvent` providers (see G-B4's row/track-b-1.20.1.md "G-B4 Forge
  as built" — this one is a known upstream quirk, not a port bug, and was left unfixed: just kill the
  process manually once its log settles).
- If you kill a hung/background Gradle run, its **child JVM may survive** even after the wrapper
  process is gone (this happened once this session with a killed `:forge:runData`). Before retrying,
  check `powershell -Command "Get-CimInstance Win32_Process -Filter \"Name='java.exe'\" | Select
  ProcessId,CommandLine"` for a leftover process holding the run's log files, and
  `Stop-Process -Id <pid> -Force` it — otherwise the retry's log cleanup (`rm` on `forge/run/logs/*`)
  fails with "Device or resource busy" and you'll misdiagnose a stale log as a live one.
