- Measure port surface by compiling, never grepping.
- Pre-commit hook's compile stage is fast and reliable; the actual `git commit` write step
  intermittently fails with "1Password: failed to fill whole buffer" or "1Password: agent returned
  an error" (GPG signing via 1Password) — just retry the same commit command.
- `:fabric:runDatagen` boots a real Fabric mod loader instance and writes generated output straight
  into `common/src/main/resources` via `copyGeneratedAssetsToCommon` — even on a FAILED run, partial
  output gets copied. It also rewrites every touched file's line endings, so a failed/successful run
  can make `git status` show thousands of false "modified" files that are pure CRLF churn. Always
  check `git -c core.autocrlf=false diff --stat` (or `--ignore-all-space`) before trusting `git
  status`'s count.
- `System.out.println`/log4j INFO lines from inside a forked datagen/gametest JVM don't reliably
  reach Gradle's captured stdout — write to a file instead, or read the run's own log file directly
  (e.g. `forge/run/logs/latest.log`/`debug.log`) rather than trusting Gradle's piped console output.
  This also applies to live `runClient` runs — Gradle's own task can print `BUILD SUCCESSFUL`/exit 0
  even when the game itself hit a fatal crash screen and the user just closed it, or when the user
  simply closed a healthy game normally (both look identical to Gradle). Always grep the run's own
  crash-reports/ and logs/latest.log if a live-play claim needs verifying, never trust the Gradle
  exit code alone.
- Mixin `@Inject`/`@Redirect`/`@WrapOperation` targets must be *declared* on the `@Mixin`-annotated
  class itself, not merely inherited. `discard()` lives on `Entity`, not `FishingHook` — targeting
  `method = "discard"` on a `@Mixin(FishingHook.class)` class fails at runtime with "could not find
  any targets matching 'discard'" (game hangs/crashes on mod load, looks like a freeze). Mixin into
  the actual declaring class and filter with `instanceof` at runtime instead.
- Verify signatures against real jars/sources via `javap`, not memory. Jar paths from the prior
  handoff are listed at the bottom of the one before that (still current, not repeated here).

    clicking at all when it happens).
  - Real cause: `FishtasticKeyBinds.fishingMinigameImpulse` (`common/src/main/java/grill24/
    fishtastic/client/FishtasticKeyBinds.java`) defaults to **SPACE** — the same physical key as
    vanilla jump — and Minecraft fires both keybindings off one physical keypress. Its
    `handleKeyPress()` used every such click to auto-reel-in and start the minigame any time
    `player.fishing != null`, with **no gate on an actual bite**. So jumping near water (e.g. off a
    dock, right after casting) with a hook out silently discarded the bobber.
  - Fix (`32c255cc`): removed the auto-reel-in branch entirely. The impulse key now only feeds
    impulse into an *already-active* minigame (its original documented purpose); starting the
    minigame stays exclusively a right-click/use-item action, matching vanilla. Confirmed fixed by
    the owner via a follow-up `runClient` session (jumped repeatedly with a hook out, no more
    auto-reel).
  - Diagnostic mixin (`EntityDiscardDiagnosticMixin`, plus its `fishtastic.mixins.json` entry) was
    removed as part of the fix commit — nothing temporary left in the tree.
